# Code Review — Civic Ledger (full codebase)
**Date:** 2026-09-30 · **Scope:** Full sweep of `ingest/`, `curation/`, `site/src/`, `site/scripts/`, `.github/workflows/`, and the committed config under `data/config/`; `data/` records, `tests/`, `site/e2e/`, docs prose, and vendored/generated paths were not reviewed · **Reviewer stance:** External senior-developer audit

## Executive Summary
This codebase is in unusually good shape for a one-person project: every published number is recomputed from committed data in CI, every ingest path fails closed (quarantine, not silent), secrets stay out of cache keys and out of URLs wherever the API allows, and the curation tool is loopback-only with CSRF protection. No finding is Critical and nothing is exploitable from the outside.

The single biggest risk is a time bomb, not a present bug. The Mississippi ingest follows "the newest regular session" automatically but never removes the previous session's files. When LegiScan publishes the 2027 session (expected January), the nightly will write it next to the 2026 data, and every Mississippi page, metric, and manifest count will silently describe two sessions while the methodology page says "only the current regular session is included." That is a Value #1 problem (a true number in a false frame), and nothing in CI would catch it. The fix is small and should land before year end.

The remaining findings are latent crash paths in the vote ingests (one bad record from the government source would abort a whole night instead of quarantining that record), a LegiScan API-key exposure in error output, and a privacy page whose current wording is stronger than the hosting setup supports. Cost of doing nothing: one surprise red nightly per crash path, and a privacy statement that could be quoted back at the operator.

## Detailed Findings

### 1. Mississippi session rollover leaves stale files behind — High
**Location:** `ingest/ms_legislature.py:392-401` (`current_session`), `:447-466` (`_export`), `ingest/checks/ms.py:34-40` (`_SAMPLES`), `site/src/pages/methods.astro:274`
**Issue:** `current_session()` picks the newest regular session from LegiScan with no config change required. `_export()` writes members, bills, votes, legislation, crosswalk, and manifest for that session but never deletes anything. The committed manifest is session 2249, "2026 Regular Session". When LegiScan adds the 2027 regular session (typically January), the nightly hash gate sees a new hash, re-ingests, and writes `ms-h-<new>-*` vote files next to the 1,725 `ms-*-2249-*` files. `ms_metrics._load_ctx()` reads every file in `data/state/ms/votes/`, so attendance, party unity, and enacted rate silently span two sessions. Member files are keyed by `people_id`: a continuing legislator's file is replaced with a 2027-only term while both sessions' votes still count against them; a legislator who left after 2026 is absent from the new people list, so their 2026 file (with `serving: true`, hardcoded at `:133`) and all their 2026 vote files stay on disk and they appear in the 2027 metrics and roster. The manifest counts only the new session. Meanwhile `methods.astro:274` publishes "Only the current regular session is included." Separately, `checks/ms.py:34-40` hardcodes five session-2249 roll ids for the official-PDF spot check; today they pass only because the old files linger, and they will report "sample or ingested roll missing" the moment the old files are cleaned.
**Why it matters:** The site would publish per-member Mississippi rates whose denominator is two sessions under copy that says one. That is exactly the "true number in a false frame" Value #1 forbids, and CI is green throughout because `checks/ms.py` recomputes from whatever is on disk. The owner would find out from a reader, not from the pipeline.
**Fix:**
1. In `run()` (`ms_legislature.py:499-509`), compare `session_row["session_id"]` to the committed manifest's `session_id`. If they differ, delete the contents of `MS_MEMBERS_DIR`, `MS_VOTES_DIR`, `MS_BILLS_DIR`, and `MS_LEGISLATION_DIR` before `_export()` (safe: export writes the complete set every time). Print one line saying which session replaced which. Plain-language consequence for the owner, to confirm before building: after rollover the 2026 `/ms/` pages stop existing (404), which is what `/methods` already promises, but if he wants past sessions to stay browsable the fix becomes a per-session directory layout instead of a delete.
2. Make `checks/ms.py` session-aware: read `session_id` from `data/state/ms/manifest.json` and skip the spot check with a printed note when it is not 2249, or key `_SAMPLES` by session so a new session can get its own samples (H-task for the owner: five new official PDFs).
3. Add a test that builds two sessions into a temp dir and asserts only the newer survives.
4. Record the decision in `docs/decisions.md` (D87) and note the spec/code disagreement in `docs/PROGRESS.md`.
**Effort:** M (about half a day including the test)

### 2. One malformed Senate `vote_date` aborts the whole run — Medium
**Location:** `ingest/senate_votes.py:321-326`
**Issue:** The pre-parse at line 322 calls `_parse_date(ET.fromstring(detail).findtext("vote_date") or "")` inside a `try` that catches only `ET.ParseError`. `_parse_date` raises `ValueError` on an unexpected format and `KeyError` on an unrecognised month name (verified: `_parse_date('')` raises `ValueError`, a bad month raises `KeyError`). Either one propagates out of `run()` and kills the process with a traceback. The later `parse_rollcall` call at line 328 does catch `ValueError`, so the guard exists but is on the wrong line.
**Why it matters:** One odd date string from senate.gov (a new date format, an empty element) turns into a full nightly failure with no quarantine file, no gap report, and no clue in the summary. Every roll after it that night goes un-ingested.
**Fix:** Change line 323 to `except (ET.ParseError, ValueError, KeyError) as exc:`. Add a unit test that feeds a detail XML with `<vote_date>garbage</vote_date>` through `run()` (mocked fetch) and asserts the roll is quarantined and the run continues.
**Effort:** S

### 3. One malformed House members response aborts the whole run — Medium
**Location:** `ingest/house_votes.py:262`
**Issue:** `date = data["houseRollCallVoteMemberVotes"]["startDate"]` runs outside the `try` that wraps `parse_rollcall` (lines 264-271). A response missing either key, or a `startDate` of `None` (then `coverage.covered_on` slices `None[:10]` and raises `TypeError`), aborts `run()` with a traceback. Same shape as finding 2.
**Why it matters:** Same as finding 2: a single bad roll from Congress.gov costs the whole night and leaves no quarantine record.
**Fix:** Move lines 262-263 inside the existing `try`, and add `TypeError` to the caught tuple on line 266. Add the matching unit test.
**Effort:** S

### 4. LegiScan API key is printed on any HTTP error — Medium
**Location:** `ingest/sources/legiscan.py:65-72`; uncaught at `ingest/ms_legislature.py:500` and `:508`
**Issue:** The key is passed as a query parameter (unavoidable with LegiScan) and `resp.raise_for_status()` raises `httpx.HTTPStatusError`, whose message is `"... for url '{0.url}'"` (verified in the installed httpx, `_models.py:744`). That URL includes `key=<secret>`. Nothing in `ms_legislature.run()` catches it, so a 4xx or 5xx from LegiScan prints the key in the traceback. The module's own docstring promises the key never reaches disk or logs; the disk half is true, the logs half is not.
**Why it matters:** GitHub Actions masks registered secrets in its log, so the nightly is protected by that layer only. A local run pastes the key into the terminal and into any log file the owner might share when asking for help.
**Fix:** In `legiscan._get`, replace `resp.raise_for_status()` with an explicit check that raises a custom `LegiScanHTTPError(f"LegiScan {op} returned {resp.status_code}")` carrying no URL. Add a test with `httpx.MockTransport` returning 500 and assert the key string is absent from `str(exc)`.
**Effort:** S

### 5. Privacy page wording is stronger than the hosting supports — Medium
**Location:** `site/src/pages/privacy.astro:16-17`, `:22-27`
**Issue:** The page says "Nothing you do here is sent to any server the operator runs" and "visiting this site leaves no record anywhere." The site is served from the operator's Cloudflare account as a Worker with static assets. Cloudflare receives every request, including the visitor's IP address, and the operator's dashboard shows aggregate request metrics for the Worker. Whether Cloudflare's edge counts as "a server the operator runs" is arguable; "no record anywhere" is not.
**Why it matters:** A false privacy statement is a Value #1 breach in the spec's own words, and V2-7 exists precisely to make this page true before any user data is stored. Today the risk is reputational: the sentence can be quoted against the operator. The wording is owner-ratified, so this is not a code edit to make unilaterally.
**Fix:** Do not edit the copy in isolation. Fold this into V2-7 task 1 (`IMPLEMENTATIONv2.md` §7 V2-7), and put the question to the owner in plain words: "The privacy page says a visit leaves no record anywhere. Cloudflare, which hosts the site, sees every visit and shows us how many requests we got. Should the page say that?" Then write the sentence the owner picks.
**Effort:** S (copy only, after the owner answers)

### 6. Absence-reason search still covers Mississippi only — Medium
**Location:** `curation/absences.py:186` (`US_STATES[config.COVERED_STATE]`) and `:191` (the call); `ingest/sources/govinfo.py:82-86` (`crec_personal_explanations` query scoped to one state)
**Issue:** `curate absences search` queries the Congressional Record for "Personal Explanation" insertions "of Mississippi" only. Since V2-1 the covered roster is all 639 members, and `data/absences/` holds about 35,600 stubs across every state, but only Mississippi members can ever have a stated reason attached. Every other member's missed vote renders "No explanation on record." (`VoteRow.astro:40`, `v/[roll].astro:150`). V2-1 task 1 said to retire the `COVERED_STATE` semantics for federal coverage; this call site was missed.
**Why it matters:** The wording is defensible (there is no explanation on the site's record), but the feature is effectively 1% built, and a reader comparing two members from different states gets asymmetric treatment, which is the shape §6.5 symmetry exists to prevent.
**Fix:** This is an owner decision, not a code change to make alone: widening the query to all 50 states multiplies the H9 review queue by roughly 50. Ask the owner in plain terms: "Right now the tool only finds absence explanations for Mississippi members. Finding them for all 639 members means many more items for you to approve by hand. Do you want that, or should the site say plainly that explanations are collected for Mississippi only?" Implement whichever answer comes back (either loop `search()` over `US_STATES`, or add one sentence to `/methods`).
**Effort:** S for either outcome

### 7. A permanently missing bill turns every nightly red — Low
**Location:** `ingest/bills.py:170-180`, `:200-203`; `ingest/cache.py:176-178`
**Issue:** A 404 from `/bill/{c}/{type}/{n}` raises `httpx.HTTPStatusError`, which lands in `fetch_failures` and returns 1 with "re-run to retry." A real 404 (a bill id the vote record cites that Congress.gov never publishes) does not go away on retry, so every nightly fails until someone intervenes. Rolls have an owner accept-list for this situation (`data/quality/accepted-quarantine.yaml`, D83); bills have none. Additionally `cache.fetch` raises before writing the cache file, so the 404 is re-requested every night.
**Why it matters:** Latent; the nightly is green today. When it fires, the owner gets a failure email every day with no way to acknowledge it short of editing code. Failing closed is the right default (every non-null `bill_id` must resolve to a bill page), so the gap is the missing acknowledgement path, not the failure.
**Fix:** Add a `bills:` section to `accepted-quarantine.yaml` (or a sibling file) and have `bills.run` treat a 404 for an accepted id as a printed note, not a failure. Optionally cache 404s in `cache.fetch` with a short TTL so the request is not repeated nightly.
**Effort:** S

### 8. Rules-Committee lookups re-fetched every night votes change — Low
**Location:** `ingest/classify.py:112-127`, `:166-174`; `ingest/sources/congress_gov.py:93-98`; `ingest/cache.py:61` (20h default TTL)
**Issue:** Pass 1 of `classify.run` collects every `hres` bill whose question starts "On Agreeing to the Resolution" (up to 215 unique ids in the current data) and fetches each one's committees sub-resource. The cache TTL is 20 hours and the nightly runs every 24, so each of those requests is stale and re-issued on every night the vote files changed. Whether a resolution was reported by the Rules Committee does not change after the fact.
**Why it matters:** At least ~4 minutes of paid Actions time per active night (1 request/second floor; D86 measured ~7 s per Congress.gov page), on a budget that ran out this month (D86).
**Fix:** Pass `ttl_hours=24 * 30` through `bill_committees` for this call (add a `ttl_hours` keyword to `bill_committees` and forward it to `_get`). One line each side.
**Effort:** S

### 9. Quarantine files are never cleared — Low
**Location:** `ingest/house_votes.py:187-192`, `ingest/senate_votes.py:247-252`, `ingest/bills.py:120-125`
**Issue:** `_quarantine()` writes `data/quality/quarantine/<id>.json`. No code path removes that file when the same roll or bill later parses and exports cleanly. Nothing reads the directory except the writers, so the only effect is stale files committed by `git add -A data/`.
**Why it matters:** Cosmetic today (four files, all owner-accepted). Over time the directory stops reflecting what is actually quarantined, which undermines its purpose as an owner-facing signal.
**Fix:** After `export_rollcall(...)` / `export_bill(...)` succeeds, `unlink(missing_ok=True)` the matching quarantine file. Three one-liners.
**Effort:** S

### 10. Weekly archive-links job pushes without rebasing — Low
**Location:** `.github/workflows/archive-links.yml:49-56`
**Issue:** The job commits `data/quality/archive-status.json` and runs a bare `git push`. If anything landed on `master` between checkout and push, the push is rejected and the report is lost. This is the exact failure D84 fixed in `nightly.yml:169-178`. The window here is minutes, not hours, and the job is a no-op until statements exist, so the risk is small.
**Why it matters:** A dead archive link would go unreported for a week.
**Fix:** Copy the fetch-rebase-retry loop from `nightly.yml:169-178` (three attempts, never `--force`).
**Effort:** S

### 11. D86 change probe has a documented-nowhere blind spot — Low
**Location:** `ingest/legislation.py:81-95` (`should_refetch`), `ingest/sources/congress_gov.py:155-170`
**Issue:** The probe compares lifetime sponsored/cosponsored counts. If a member gains one cosponsorship and withdraws another between two nightlies, the count is unchanged and the member is not re-paged until the Sunday `--full` run. The module docstring names one blind spot (an enactment with no new sponsorship) but not this one. Whether `cosponsoredLegislation.count` excludes withdrawn items could not be confirmed from the code alone.
**Why it matters:** Bounded to 7 days of staleness, same as the documented case, so no published number is wrong for longer than the design already accepts.
**Fix:** Confirm against one live `/member/{id}` response whether the count moves on a withdrawal, then add one sentence to the `legislation.py` module docstring and to D86 in `docs/decisions.md`.
**Effort:** S
